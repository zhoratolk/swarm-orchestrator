# swarm-orchestrator

Рой моделей поверх стороннего шлюза (`api.experientiallabs.ai`), не через Task/Agent — токены Claude Code не тратятся, всё летит по HTTP к бесплатным (в основном) моделям шлюза. Полный протокол ролей — [`PROTOCOL.md`](PROTOCOL.md). Реализация — пакет [`swarm/`](swarm).

## Когда использовать

Юзер просит прогнать задачу автономно, «запустил и забыл»: разложить цель на подзадачи, раздать нескольким моделям параллельно, свести, отревьюить, сдать. Не для быстрых одноразовых правок — для задач, которые реально выигрывают от параллельного роя разных моделей и от проверки результата независимыми проверяющими.

## Как запускать

1. Ключ шлюза в переменной окружения, никогда в файле:
   ```bash
   export EXPLABS_API_KEY=xpl_...
   ```
   Скопировать `env.example` в `.env` и вписать ключ — `orchestrator.py` подхватит сам (`python-dotenv`), либо экспортировать в шелле напрямую.

2. Поставить зависимости (минимум, без лишнего):
   ```bash
   pip install -r requirements.txt
   ```

3. Описать задачу в YAML (см. `examples/example_task.yaml`) — цель, и опционально готовый список задач с зависимостями и командой проверки (`verify_cmd`) для каждой. Если задач нет — Менеджер разложит цель сам первым вызовом.

4. Запуск:
   ```bash
   python -m swarm.orchestrator run examples/example_task.yaml
   ```
   Без ключа и без сети — сухой прогон на заглушке, чтобы проверить, что цикл вообще ходит по кругу и не виснет:
   ```bash
   python -m swarm.orchestrator run examples/example_task.yaml --dry-run
   ```

5. Смотреть на `run.log` в рабочей директории и на файл доски задач `board.json` — он же чекпоинт, `--resume` продолжает с того же места, если процесс прервали.

6. В конце — `report.md`: сколько вызовов, токенов, фактическая стоимость (по `usage.cost`), теневая (по прайс-таблице в `swarm/gateway.py`, приколота вручную под OpenRouter — раз в несколько месяцев стоит свериться и поправить руками, живого фетча нет намеренно, чтобы инструмент не ломался от чужого API).

## Что важно знать до запуска

- Диспетчер решает, сколько агентов и каких спавнить, но каждый спавн сначала проходит Ревизора (`swarm/roles.py::SpawnAuditor`) — жёсткий лимит на параллельных агентов задачи, запрет повторного спавна той же роли без причины, при спорных случаях (N>3 или повтор) — отдельный LLM-вызов на подтверждение. Без этого рой имеет свойство расплодиться на ровном месте.
- Приёмщик не верит `self_check` агентов на слово: у каждой задачи в YAML можно задать `verify_cmd` — реальную shell-команду (`test -f ...`, `pytest ...`, `curl ...`), и Приёмщик прогоняет её сам локально перед тем как закрыть задачу.
- Платные модели по умолчанию выключены (`ALLOW_PAID: false` в конфиге задачи) — включать явно, если правда нужно.
- Секреты и персональные данные из текста задачи, который летит наружу, чистит `swarm/scrub.py` (ключи, токены, email, телефоны, ИИН/БИН-подобные числа) — грубый regex-фильтр, не панацея, для по-настоящему чувствительного вообще не гонять через внешний шлюз.

## Файлы

- `PROTOCOL.md` — полная спека ролей и правил, читать первым, если меняешь логику.
- `swarm/gateway.py` — HTTP-клиент шлюза: ретраи, ограничения моделей, прайс-таблица.
- `swarm/contract.py` — JSON-контракт агента, парсинг и валидация ответа, повтор при браке.
- `swarm/board.py` — доска задач, персистентность, резюме прогона.
- `swarm/scrub.py` — фильтр секретов/ПД перед отправкой наружу.
- `swarm/roles.py` — Менеджер, Диспетчер, Ревизор, Приёмщик: построение промптов и решения.
- `swarm/orchestrator.py` — главный цикл и CLI (`run`, `--resume`, `--dry-run`).
