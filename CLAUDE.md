# swarm-orchestrator — как с ним работать

Автономный рой моделей поверх шлюза Experiential Labs. Обычный Python-процесс, не субагенты
Claude Code. Полное описание архитектуры — [PROTOCOL.md](PROTOCOL.md), пользовательский обзор —
[README.md](README.md). Этот файл — практический плейбук для чата, который будет запускать рой.

## Быстрый запуск

```bash
cd D:\swarm-orchestrator
python -m swarm.orchestrator run examples/example_task.yaml --dry-run   # без ключа, проверить цикл
python -m swarm.orchestrator run examples/example_task.yaml             # с реальным ключом
```

Ключ — в `D:\swarm-orchestrator\.env` (`EXPLABS_API_KEY=...`), подхватывается сам через
`python-dotenv`. Каждый worktree/копия видит только свой `.env` — если запускаешь рой не из
`D:\swarm-orchestrator`, а из воркчасти, либо клади туда свой `.env`, либо перед запуском:
`$env:EXPLABS_API_KEY = [Environment]::GetEnvironmentVariable("EXPLABS_API_KEY","User")` — но это
сработает только если ключ реально прописан в User-переменных через `setx`, а не только в `.env`.

## Перед КАЖДЫМ запуском — проверить, что не крутится другой прогон

Два процесса оркестратора на одном `--run-dir` калечат друг другу `board.json` — было на живую
пойманное поведение, не гипотеза. Перед `run`:

```powershell
Get-CimInstance Win32_Process -Filter "Name='python.exe'" | Select-Object ProcessId
```

Пусто — можно стартовать. Если что-то есть и это не твой процесс — не трогать чужую работу.

## Правишь чужой код (не тривиальную задачу с нуля) — используй `repo_context`

Рой не умеет читать файлы сам (нет tool use, только текст задачи). Чтобы Менеджер/Диспетчер/агенты
видели реальный код, а не только текст цели — добавь в YAML задачи:

```yaml
repo_context:
  - "src/**/*.py"        # glob-паттерны относительно рабочей директории запуска
```

Прокидывается во ВСЕ вызовы: `manager_decompose`, `manager_replan`, `dispatcher_plan`, каждую волну
агентов. Лимит 400К символов, режется с предупреждением в лог, если превышен.

## Рой работает на СВОЁМ или ЧУЖОМ репозитории — ТОЛЬКО в изолированном git worktree

Никогда не давай рою писать прямо в рабочую копию, которой пользуешься сам, и никогда — в
`main`/`master`. Свободная бесплатная модель без ревью человека не должна иметь прямой путь в
боевую ветку. Паттерн (проверен дважды: самоулучшение swarm-orchestrator, правка vtube-acmt):

```bash
git worktree add ../<name>-swarm -b swarm/<topic> <base-branch>
cd ../<name>-swarm
# запустить рой здесь, с --run-dir своим, goal/tasks описывают конкретную находку/задачу
```

После прогона: **сам прочитай `git diff` в этой ветке**, ничего не мержи/не пуши вслепую. Если
патч хороший — смержить в исходную ветку (или `cherry-pick` в основной чекаут, если правка не
специфична для ветки) и спросить юзера перед пушем на `origin`, если это публичный/чужой репозиторий.
Для чужого репо (не свой) — вообще не пушить и не открывать PR без явного разрешения юзера, только
показать диф и объяснение.

## Известные особенности живых прогонов (не баги, если понимаешь причину)

- Свободные модели (`gpt-6-*`, `claude-opus-5.5`) иногда обрывают ответ по `stop_reason=max_tokens`
  — `call_agent` в этом случае сам удваивает бюджет и повторяет, лечить руками не нужно.
  `claude-fable-5.1` — недоступна тарифом (429), `jev` — отдельный несовместимый бэкенд, оба уже
  в списке `UNAVAILABLE`, не пытаться чинить.
- 403 с Anthropic/OpenAI-семейств моделей на части сетей — геоблок апстрима, не баг шлюза; `Gateway`
  сам метит модель мёртвой на прогон и уходит на фолбэк (`nemotron-3-ultra-550b-a55b`, всегда
  доступна). Если фолбэк тоже недоступен — тогда уже реальная проблема с сетью/ключом.
- Ревью/Приёмщик реально выполняют `verify_cmd` на машине — не верят `self_check` агентов. Если
  задача не про запись файла (например review чужого архитектурного решения), `verify_cmd` можно не
  задавать, но тогда приёмка честно останется частично на self-report.
- `cost_cap` в YAML — это $-бюджет по факту потраченного (обычно копейки на бесплатных моделях), не
  лимит на количество вызовов. `allow_paid: false` по умолчанию — платные модели не трогать без
  явного `true` и осознанного решения юзера.

## Файлы

- `PROTOCOL.md` — полная спека ролей (Менеджер/Диспетчер/Ревизор/Ревьюеры/Приёмщик), читать перед
  изменением логики `swarm/roles.py`.
- `examples/example_task.yaml` — простой эталонный прогон (is_prime), должен всегда проходить
  `--dry-run` и живой прогон без падений — регрессионный чек-лист после любой правки `swarm/`.
- `examples/example_research_task.yaml` — сложнее (research→implement→tests), показывает
  адаптивный спавн исследователей/аналитиков.
