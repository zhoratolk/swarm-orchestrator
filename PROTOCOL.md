# Протокол роя

Полная спека ролей, контракта и правил. `orchestrator.py` реализует этот протокол; если меняешь один — меняй и второй.

## 0. Задача верхнего оркестратора

Оркестратор (скрипт `orchestrator.py`, не LLM-роль) держит цикл выполнения, лимиты стоимости, ретраи HTTP-уровня и условия остановки. Он не решает *что* делать — это Менеджер; не решает *кого спавнить* — это Диспетчер. Он крутит цикл, пишет чекпоинты, обрывает по стоп-условиям.

Тяжёлую работу — генерацию кода, исследование, анализ, ревью — делают модели шлюза. Токены Claude Code не тратятся: агенты роя — это HTTP-вызовы к `api.experientiallabs.ai`, не Task/Agent-субагенты.

## 1. Критично: чем агент НЕ является

Агенты этого роя — HTTP-вызовы к шлюзу, а не субагенты Claude Code. Параллелизм — это скрипт, стреляющий несколькими запросами одновременно (`ThreadPoolExecutor` в `gateway.py`), а не спавн Task.

## 2. Доступ

```
EXPLABS_API_KEY=xpl_...
BASE=https://api.experientiallabs.ai
```

Ключ только из переменной окружения. Не в промпте, не в коде, не в логе.

| Эндпоинт | Формат | Когда |
|---|---|---|
| `/v1/messages` | Anthropic Messages | по умолчанию, работает со всеми слагами |
| `/v1/chat/completions` | OpenAI Chat | если нужен OpenAI-специфичный параметр |

## 3. Модели роя

Бесплатность проверяется полем `usage.cost` фактического ответа, не декларацией.

**Бесплатные (`cost = 0.0`):** `claude-opus-5.5`, `gpt-6-sol`, `gpt-6-luna`, `gpt-5.6-luna`, `nemotron-3-ultra-550b-a55b`.

**Платные — не брать без явного разрешения (`ALLOW_PAID: true` в задаче):** `gpt-6-astra`, `claude-sonnet-5`, `gpt-5.6-terra`, `qwen3.8-27b`, `deepseek-v4-flash`.

**Недоступные:** `claude-fable-5.1` (429 `model_requires_purchase`), `jev` (не Messages-бэкенд, отдельный `/v1/systemone`, агентом роя не использовать).

**Особенности:** GPT-семейство требует `max_tokens >= 16` (иначе 400). `gpt-6-sol` игнорирует `reasoning` в параметрах. Расширенное мышление нативно только на Anthropic-маршрутах. Аптайм неодинаков (`gpt-6-sol` 100%, `gpt-6-luna` 99.9%, `claude-opus-5.5` 94.6%) — ретраи обязательны.

## 4. Роли роя

| Роль | Модель по умолчанию | Задача |
|---|---|---|
| **Менеджер** (был «планировщик») | `claude-opus-5.5` | Раскладывает цель на задачи и волны один раз в начале, дальше держит доску состояний (`queued/dispatched/in_progress/needs_review/blocked/done`), перепланирует при блокерах от Диспетчера или `reject` от Приёмщика, решает эскалацию человеку. Сам агентов не спавнит — только ставит задачи Диспетчеру. |
| **Диспетчер** | `gpt-6-luna` | Единственный спавнер. Получает открытую задачу от Менеджера, сам решает состав: сколько Исследователей/Аналитиков (не фиксировано — по сложности), когда нужен Сверщик, когда — Ревьюеры, когда задача не ложится ни в одну роль — спавнит Специалиста. Каждый спавн сначала идёт через Ревизора. Отчитывается Менеджеру сжатой сводкой, не сырыми ответами. |
| **Ревизор спавна** | правила + `nemotron-3-ultra` на спорные случаи | Следит за Диспетчером: не даёт плодить агентов без нужды. Жёсткие лимиты (максимум одновременных агентов на задачу, запрет повторного спавна той же роли без изменившейся причины, стоп по бюджету), для пограничных случаев (N>3, повтор роли, специалист) — отдельный LLM-вызов на подтверждение необходимости. Вето Ревизора обязательно к исполнению. |
| **Исследователь ×N** | `gpt-6-sol` / `gpt-6-luna` | N решает Диспетчер под задачу |
| **Аналитик ×N** | `gpt-5.6-luna` | N решает Диспетчер под задачу |
| **Реализатор ×N** | `gpt-6-sol` + `claude-opus-5.5` | По одной независимой задаче на агента, параллельно |
| **Сверщик ×N** | `gpt-6-luna` | Спавнится по поводу: после волны разведки (противоречия), после волны реализации (конфликт файлов/решений), отдельно под реализатора с самостоятельным архитектурным решением |
| **Ревьюер кода/архитектуры/решений ×3+** | занятые модели, ≠ автор | На каждый готовый артефакт, минимум 3 разные модели, автор себя не ревьюит |
| **Специалист (кастомный)** | любая свободная модель, задаётся Диспетчером | Под задачу, не описанную ни одной ролью выше (конвертация, разовый расчёт, проверка лицензии). Контракт тот же, `role="specialist"`, свободное поле `task_description` |
| **Приёмщик** | `claude-opus-5.5` + `gpt-6-sol` | Двойная проверка: 1) сверка результата с исходной целью, не со списком задач; 2) верификация реального состояния — сам выполняет `verify_cmd` задачи (shell-команда, файл, HTTP-проверка), не доверяет `self_check` агента на слово |

Все роли, кроме Менеджера, Диспетчера и Ревизора, порождаются и умирают по задаче — постоянного пула нет.

**`verify_cmd` и command injection.** `verify_cmd` — реальная shell-команда, исполняется Приёмщиком
через `subprocess.run(shell=True)`. Если задачи заданы человеком в YAML — это ожидаемо: пользователь
сам написал команду. Но при авто-декомпозиции цели Менеджер (бесплатная LLM за внешним шлюзом) сам
вписывает `verify_cmd` в план — без гейта это произвольный shell-доступ к машине от модели, ответ
которой никто не читал. Поэтому `verify_cmd_source` ("user" | "llm") едет вместе с задачей, и
Приёмщик выполняет только `"user"`; `"llm"`-команда пропускается (приёмка остаётся на
ревью-кворуме/self-report — как для задачи без `verify_cmd` вообще), пока в конфиге явно не стоит
`allow_llm_verify_cmd: true`.

## 5. Контракт агента

Каждый агент обязан вернуть только JSON по этой схеме. Текст вне JSON — брак, запрос повторяется с уточнением (см. `contract.py::call_agent`, до 2 повторов).

```json
{
  "role": "implementer | reviewer | researcher | analyst | manager | dispatcher | checker | specialist | acceptor",
  "task_id": "строка",
  "spawned_by": "кем и по какому поводу порождён — для трассировки динамического роя",
  "status": "done | blocked | needs_info",
  "confidence": 0.0,
  "result": "суть, сжато",
  "artifacts": [{"path": "путь", "action": "create|modify|delete", "content": "..."}],
  "tools_used": [{"name": "имя", "input": {}, "ok": true}],
  "findings": [{"severity": "blocker|major|minor", "what": "", "where": "", "fix": ""}],
  "assumptions": ["что принято без доказательства"],
  "blocked_reason": "заполняется только при status=blocked",
  "self_check": {"goal_met": false, "why": ""}
}
```

Отчёт Диспетчера Менеджеру — отдельная, более узкая схема:

```json
{"task_id": "", "board_delta": [{"id": "", "status": ""}], "blockers": [], "spawned_this_round": [{"role": "", "model": "", "count": 0, "reason": ""}]}
```

Проверки над каждым ответом агента:

- JSON валиден и схема соблюдена — иначе повтор запроса.
- `status=done` при пустом `result` — брак.
- `confidence` выше 0.8 при непустых находках уровня `blocker` — противоречие, запросить объяснение.
- `assumptions` не пуст и не содержит выдуманных фактов, где это проверяемо.

## 6. Кворум ревью

Минимум три разные модели на каждый значимый артефакт. Вердикт: `approve` / `approve_with_findings` / `reject`. Любой `reject` блокирует приёмку независимо от большинства. Расхождение вердиктов не усредняется — спорный пункт идёт отдельным запросом всем ревьюерам с аргументами обеих сторон. Находка уровня `blocker` от любой модели — итерация не закрывается.

## 7. Цикл выполнения

```
1. ПЛАН         Менеджер -> задачи, волны, критерии приёмки, verify_cmd на задачу
2. РАЗВЕДКА     Менеджер просит разведку -> Диспетчер решает состав -> Ревизор одобряет -> волна
3. СВЕРКА       Диспетчер спавнит Сверщика на противоречия разведки -> уточняющий раунд при расхождении
4. РЕАЛИЗАЦИЯ   аналогично: Менеджер просит реализацию -> Диспетчер -> Ревизор -> волна реализаторов
5. СВЕРКА       Сверщик на конфликты между параллельными результатами
6. РЕВЬЮ        Диспетчер спавнит >=3 ревьюеров на готовый артефакт -> кворум
7. ПРИЁМКА      Приёмщик: цель + реальное состояние машины (verify_cmd)
8. РЕШЕНИЕ      все ок -> конец. Иначе находки -> Менеджеру, следующая итерация
```

Волны запускаются параллельно одним пулом потоков, не последовательными вызовами. Задачи в одной волне не трогают одни и те же файлы (проверяется Сверщиком).

## 8. Условия остановки

- **Успех.** Приёмщик вернул `goal_met: true` по обеим проверкам (цель + реальное состояние) и нет находок уровня `blocker`.
- **Невыполнимое условие.** Агент вернул `blocked`, минимум две другие модели подтвердили невыполнимость в принципе. Менеджер формулирует, что именно невозможно.
- **Застой.** Три итерации подряд без сокращения числа находок уровня `blocker` — остановка, эскалация человеку с описанием, на чём заклинило.
- **Предохранитель.** Суммарная стоимость превысила заданный потолок (`cost_cap` в конфиге задачи), либо шлюз устойчиво отдаёт 429 — остановка с сохранением состояния (`board.json`), резюме через `--resume`.

## 9. Безопасность и персональные данные

Данные уходят наружу, к стороннему провайдеру.

- Фильтр перед каждым вызовом (`scrub.py`): ключи и токены, пароли, строки подключения к БД, содержимое `.env`, ФИО, телефоны, адреса, ИИН/БИН-подобные числа, платёжные данные. Вместо секрета — плейсхолдер `<SECRET:тип>`.
- Ключ шлюза только из переменной окружения.
- Для чужих данных — только модели с `no_training: true`: `claude-opus-5.5`, `gpt-6-sol`, `gpt-6-luna`. У `gpt-5.6-luna` политика не заявлена, у `nemotron-3-ultra` обучение не запрещено — им чужое не отдавать.
- Нулевого хранения (`zdr`) у этих моделей нет — логи у провайдера остаются. Для по-настоящему чувствительного шлюз не использовать вовсе.
- В ответах агентов секреты не восстанавливать.

## 10. Учёт токенов и стоимости

Шлюз возвращает факт в каждом ответе: `"usage": {"input_tokens": N, "output_tokens": N, "cost": 0.0, "is_byok": false}`.

Два счётчика: фактический расход (сумма `usage.cost`) и теневая стоимость — прайс-таблица в `gateway.py::SHADOW_PRICES`, составлена вручную один раз по `openrouter.ai/api/v1/models` и приколота в файле (живого фетча каждый прогон нет намеренно — чтобы инструмент не ломался от чужого API и не бил лишний раз по сети). Раз в несколько месяцев свериться и поправить руками.

Стоимость считается по каждой итерации отдельно.

## 11. Устойчивость

- Ретрай с экспоненциальной задержкой на 429 и 5xx: 1с, 2с, 4с, 8с, максимум 5 попыток.
- Устойчивый 429 на конкретной модели — вывести из пула на текущую задачу, перераспределить на живые, зафиксировать в отчёте.
- Ошибка 400 `max_tokens must be at least 16` — поднять лимит и повторить.
- Ошибка 429 `model_requires_purchase` — модель недоступна тарифом, исключить навсегда на этот прогон.
- Таймаут на вызов обязателен; зависший агент не блокирует волну, задача уходит другой модели.
- Промо-статус временный: если бесплатная модель начала возвращать ненулевой `cost` — остановиться и сообщить, не продолжать молча.

## 12. Чего оркестратор не делает

- Не пересказывает полные ответы агентов — только сводки и расхождения.
- Не пишет код сам, пока рой справляется.
- Не принимает работу по заявлению агента — только по сверке с целью и реальным состоянием.
- Не закрывает итерацию при неразрешённом расхождении ревьюеров.
- Не отправляет наружу то, что не прошло фильтр персональных данных.
- Не даёт Диспетчеру спавнить в обход Ревизора.
